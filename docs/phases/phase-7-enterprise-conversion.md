# Phase 7 — Enterprise & Conversion

## Positioning

ThreatFade is presented as a specialized, evidence-first detection and investigation layer. The enterprise experience does not claim to replace a SIEM/SOAR and does not invent certifications, customers, performance guarantees or compliance commitments.

## Audience journeys

- **SOC leaders:** detection → evidence → integration → evaluation
- **Security architects:** architecture → security boundary → deployment → evaluation
- **Security engineering:** detection packs → API/exports → validation → evaluation
- **Platform teams:** deployment → identity → persistence → operations
- **Research organizations:** methodology → benchmarks → evidence → evaluation
- **Qualified buyers:** technical scope → evaluation request

## Deployment boundary

The engine documents an Enterprise IdP feeding an OIDC/JWT boundary, a ThreatFade control plane, a detection data plane, tenant-scoped PostgreSQL persistence, object/export storage and operational telemetry. Outputs include JSON, Sigma-compatible, STIX 2.1-compatible, SIEM and FusionOps paths.

## Conversion policy

Primary calls to action are technical: run ThreatFade, read documentation, explore research, view GitHub and request a scoped evaluation. A generic demo-first funnel is intentionally avoided.

## Lead handling

No public lead database or arbitrary form endpoint is required for this phase. The evaluation CTA uses an explicit email action, avoiding a new unauthenticated server-side input boundary until there is a justified operational need for structured lead capture.

## Claims boundary

Enterprise pages must not imply SOC 2/ISO certification, third-party testing, independent detection validation, contractual SLAs, customer-scale guarantees, data residency commitments or customer logos unless independently evidenced and added later.
