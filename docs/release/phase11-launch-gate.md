# Phase 11 — Final production launch gate

## Release decision

The website is release-ready only when the checks below are green on the release candidate and the deployed target has been smoke-tested.

### Architecture

- [x] Marketing, research, docs, playground and enterprise surfaces remain separate concerns.
- [x] Engine communication is isolated behind `lib/api/` and validated models.
- [x] Browser components do not construct engine URLs or handle engine credentials.
- [x] Curated playground input remains separate from production engine detection.
- [x] No new database, CMS, monorepo, or public proxy abstraction is required.

### Product and claims

- [x] Product positioning is evidence-first and avoids unsupported guarantees.
- [x] Developer path leads to GitHub, run instructions and contribution paths.
- [x] Research path leads to methodology, evidence and source material.
- [x] SOC path leads to detection, evidence, playground and deployment material.
- [x] Enterprise path explains evaluation without fabricated customer proof.
- [x] Engine repository is the source of truth for implemented capability claims.

### Security

- [x] Production security headers and CSP are configured in `next.config.ts`.
- [x] Engine API requests are server-side, bounded, schema-validated and redirect-disabled.
- [x] Public playground input is allowlisted and size/rate bounded.
- [x] No public arbitrary PCAP processing boundary exists.
- [x] No engine credentials are exposed through browser code or `NEXT_PUBLIC_*` configuration.
- [x] Dependency audit and CodeQL are required CI gates.

### Accessibility

- [x] Semantic landmarks and heading hierarchy are part of the shared page architecture.
- [x] Keyboard/focus states and reduced-motion behavior are implemented in shared primitives.
- [x] Interactive visualizations provide textual context rather than relying on color alone.
- [ ] Manual assistive-technology verification remains a release-owner responsibility; CI cannot certify every screen-reader/browser combination.

### SEO and discovery

- [x] Canonicals, metadata, robots and sitemap are generated by the App Router metadata architecture.
- [x] Organization, software, research/article and breadcrumb structured data is evidence-bounded.
- [x] Research and documentation use explicit terminology, dates, references and status boundaries.
- [x] Internal linking connects product, research, docs, playground and GitHub paths.

### Performance

- [x] Server Components are the default boundary.
- [x] Interactive code is isolated to client components where necessary.
- [x] Images/fonts use framework-aware loading paths.
- [x] Motion respects reduced-motion preferences.
- [ ] Real-user Core Web Vitals require production telemetry; CI cannot honestly guarantee field LCP/INP/CLS thresholds.

### Required automated gates

```text
format:check
lint
typecheck
unit tests
npm audit --audit-level=high
production build
Playwright E2E
Security workflow
CodeQL workflow
```

### Required release smoke test

After deployment, verify `/`, `/product`, `/detection`, `/how-it-works`, `/integrations`, `/security`, `/research`, `/docs`, `/playground` and `/enterprise`; verify canonical URLs, sitemap/robots, no console errors, mobile navigation, GitHub links, and the curated playground's no-verdict boundary.

### Explicit limitations

A green CI pipeline is evidence of automated verification, not a security certification, accessibility certification, performance guarantee, or independent validation. Production readiness remains conditional on the deployment environment, DNS/TLS configuration, environment variables, observability and real-user telemetry.
